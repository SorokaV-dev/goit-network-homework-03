# Діагностика та безпека мереж — домашня робота №5

## 1. TCP handshake у tcpdump

Команда захоплення:

```bash
sudo tcpdump -i any port 80 -c 10
```

Під час захоплення виконано:

```bash
curl -I http://example.com
```

Перші пакети:

```text
192.168.5.1.52850 > 172.66.147.243.80: Flags [S], seq 1560752542, length 0
172.66.147.243.80 > 192.168.5.1.52850: Flags [S.], seq 1018772295, ack 1560752543, length 0
192.168.5.1.52850 > 172.66.147.243.80: Flags [.], ack 1, length 0
192.168.5.1.52850 > 172.66.147.243.80: Flags [P.], seq 1:76, ack 1, length 75: HTTP: HEAD / HTTP/1.1
172.66.147.243.80 > 192.168.5.1.52850: Flags [P.], seq 1:321, ack 76, length 320: HTTP: HTTP/1.1 200 OK
```

Послідовність `[S]` → `[S.]` → `[.]` — це успішний three-way TCP handshake: клієнт надсилає SYN, сервер відповідає SYN+ACK, клієнт підтверджує ACK. Прапорець `[P.]` означає PSH+ACK: сегмент містить дані, які TCP має передати застосунку без очікування заповнення буфера. У capture `[P.]` містить HTTP-запит і відповідь сервера.

## 2. Reverse Proxy

Конфігурація:

```nginx
location /api {
    proxy_pass http://localhost:3000;
    proxy_set_header X-Real-IP $remote_addr;
}
```

`proxy_set_header X-Real-IP $remote_addr` передає бекенду реальну IP-адресу клієнта. Без цього бекенд бачив би адресу reverse proxy, що ускладнює логи, rate limiting, аудит і виявлення зловживань.

`proxy_pass` дозволяє залишити порт 3000 закритим від інтернету: зовні доступний лише Nginx, який може завершувати TLS, застосовувати обмеження запитів, перевірки заголовків і правила доступу. Це зменшує поверхню атаки бекенду.

## 3. Алгоритм балансування

Для stateful-сесій у локальній пам'яті обираю **IP Hash**. Він прив'язує запити одного клієнта до того самого backend за його IP-адресою, тому сесія частіше потрапляє на сервер, де була створена.

Round Robin розподіляв би послідовні запити між різними серверами. Якщо сесія є лише в пам'яті першого сервера, наступний запит до іншого сервера не знайде її: користувач може виглядати розлогіненим або втратити стан. Надійніша довгострокова альтернатива — винести сесії у спільне сховище, але для описаної архітектури IP Hash вирішує проблему липких сесій.

## 4. Мікросегментація в Kubernetes

```yaml
spec:
  podSelector:
    matchLabels:
      app: database
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: backend
```

Правило застосовується до Pod-ів з міткою `app: database`. Ingress до них дозволено лише Pod-ам з міткою `app: backend` у тому самому namespace, якщо політика не доповнена іншими namespace selectors.

Якщо фронтенд буде скомпрометований, його Pod не має мітки `app: backend`, тому не зможе напряму звернутися до database Pod-ів. Це обмежує blast radius: інцидент у фронтенді не дає автоматичного мережевого доступу до бази даних.

## 5. IDS та Defense in Depth

IDS фіксує та сповіщає про подію `ET EXPLOIT POSSIBLE SQL Injection (UNION SELECT)`, але зазвичай не блокує пакет. IPS працює inline і, за відповідним правилом у режимі prevention, могла б відкинути пакет або розірвати з'єднання до того, як запит дійде до застосунку.

На edge-рівні таку атаку може зупинити WAF: правила WAF виявляють характерні SQL Injection патерни й блокують або challenge-запити до потрапляння в мережу застосунку. Це один з шарів Defense in Depth разом із параметризованими SQL-запитами, валідацією вводу та мінімальними правами облікового запису БД.
